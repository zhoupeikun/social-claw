## 二、技术架构复盘

### 2.1 数据层

```
┌─────────────────────────────────────────────────────────┐
│                        数据层                            │
├─────────────────────────────────────────────────────────┤
│  微博数据 (5960条)      →  weibo_final.json              │
│  微博评论 (168条)       →  weibo_comments.json           │
│  即刻动态 (20条)        →  jike_posts_full.json          │
│  人格档案               →  persona_profile_enhanced.json │
│  Token 存储             →  jike_tokens.json              │
└─────────────────────────────────────────────────────────┘
```

**技术选型**: JSON 文件存储，简单直接，适合原型阶段。

**问题**: 没有统一的数据库，数据之间关联性弱。

### 2.2 平台适配层（即刻）

**方案演进**:

| 阶段 | 方案 | 结果 | 原因 |
|------|------|------|------|
| v1 | 直接 API 调用 | ❌ 失败 | `web-api.okjike.com` 返回 503 |
| v2 | Token + API 探测 | ⚠️ 部分 | 找到 API 端点但无法直接调用 |
| v3 | Playwright 浏览器自动化 | ✅ 成功 | 扫码登录 + 模拟用户操作 |
| v4 | Token 持久化 + 浏览器 | ✅ 稳定 | 保存 JWT Token，减少扫码次数 |

**最终方案**: Playwright 浏览器自动化 + Token 持久化

```python
# 核心流程
扫码登录 → 提取 localStorage Token → 保存到文件 → 下次注入 Token 自动登录
```

### 2.3 内容生成层

**架构**:
```
用户 Memory → Prompt 构建 → DeepSeek API → 内容生成 → 隐私检查 → 人工确认 → 发布
```

**关键设计**:
- 基于真实 memory 构建 Prompt Context，禁止编造
- 双模式人格：工作模式（专业/简洁）vs 生活模式（轻松/幽默）
- 隐私脱敏：手机号、地址、真实姓名自动过滤
- 人工确认：前期所有内容需用户确认后才发布

### 2.4 调度层

**当前状态**: 手动触发，未实现自动化调度

**计划方案**:
```
定时任务 (cron) → 内容生成 → 人工确认 → 浏览器自动化发布
```

## 三、技术方案 Review

### 3.1 做得好的

| 方面 | 说明 |
|------|------|
| **数据驱动** | 5960 条微博数据完整采集，人格分析有真实依据 |
| **渐进式实现** | 从 API 到浏览器自动化，快速验证可行性 |
| **Token 持久化** | JWT Token 保存方案，减少重复扫码 |
| **隐私保护** | 明确的隐私边界和脱敏规则 |
| **人工确认机制** | 前期所有操作需确认，风险控制到位 |
| **真实记忆生成** | 基于真实读过的书、说过的话生成内容，不编造 |

### 3.2 技术债务

| 问题 | 影响 | 建议 |
|------|------|------|
| 无数据库 | 数据关联弱，查询效率低 | 后期迁移到 SQLite/PostgreSQL |
| 硬编码选择器 | 即刻页面变化会失效 | 增加选择器容错机制 |
| 无图片上传 | 带图帖子互动率 +167% | 优先实现图片上传 |
| 无定时调度 | 需手动触发 | 用 cron/APScheduler 实现 |
| 无评论互动 | 社交属性弱 | 实现评论/点赞/关注 |
| Cookie 持久化未完成 | Token 会过期 | 实现自动刷新机制 |

### 3.3 架构缺陷

**当前架构**:
```
脚本级实现 → 功能分散 → 难以维护
```

**理想架构**:
```
claw/
├── data/              # 统一数据存储
├── adapters/          # 平台适配器（即刻/小红书/微博）
├── core/              # 人格引擎、内容生成、隐私保护
├── scheduler/         # 定时任务、自动发布
└── web/               # 管理界面（可选）
```

**差距**: 目前还是脚本集合，未形成模块化架构。

## 七、经验教训

### 7.1 技术经验

1. **API 探测 vs 浏览器自动化**
   - 现代 Web 应用 API 防护严格，直接调用困难
   - 浏览器自动化虽然慢，但成功率更高
   - Token 持久化是减少人工干预的关键

2. **选择器维护**
   - 前端页面结构变化频繁
   - 需要多选择器容错机制
   - 截图调试是定位问题的有效手段

3. **内容生成**
   - 基于真实 memory 的生成比模板效果更好
   - Prompt Engineering 比微调模型更实用
   - 隐私检查必须在生成后、发布前执行

### 7.2 产品经验

1. **数字分身定位**
   - 不是替代你，而是辅助你
   - 人格要有真实根基，不能凭空编造
   - 隐私边界必须清晰

2. **运营节奏**
   - 前期慢比快好，建立信任
   - 人工确认是必要成本
   - 内容质量 > 发布频率

### 7.3 协作经验

1. **需求澄清**
   - 早期对"基于 memory 生成"理解不一致
   - 需要明确区分"真实记忆"和"编造内容"

2. **迭代节奏**
   - 快速验证（浏览器自动化）> 完美方案（API 调用）
   - 先跑通再优化
